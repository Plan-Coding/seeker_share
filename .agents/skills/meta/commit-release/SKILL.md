# 提交与发布流程(Commit & Release)

## 版本记录

- 版本号从 `0.0.1` 起(SemVer),记录**两处且必须一致**:
  - `pom.xml` 的 `<version>`(不带 `-SNAPSHOT`)
  - Git tag `vX.Y.Z`
- 当前最新版本以最新 tag 为准;`pom.xml` 版本应始终等于最新 tag 版本。

## 递增规则(SemVer)

| 位 | 版本 | 适用 |
| --- | --- | --- |
| PATCH | `0.0.x` | 修复、文档、文案、小调整 |
| MINOR | `0.x.0` | 新功能、向后兼容增强(默认档) |
| MAJOR | `x.0.0` | 破坏性变更(0.x 阶段基本不用) |

## 分支策略

- `main` = 稳定发布分支,永远可构建,与最新 tag 一致。
- **新功能**:默认从 main 切 `feature/<名称>` 分支开发,完成后合回 main。
- **修复 / 文档**:默认在当前分支(通常是 main)直接提交,不新开分支。

## 提交流程

1. **定性**:判断本次属于 新功能 / 修复 / 文档 / 重构。
2. **版本询问**:
   - 若是**新功能或功能合入** → 必须向用户确认:**新版本 or 当前版本?**
     - 当前版本 → 不升号,正常提交。
     - 新版本 → 按类型**建议**目标版本号(默认 MINOR+1,即 `0.x+1.0`),**等用户确认**后:
       1. 更新 `pom.xml` `<version>`(去掉 `-SNAPSHOT`)
       2. 提交 → 合入 `main` → 在 main 上打 tag `vX.Y.Z` → 推送(含 tag)
   - 若是**修复 / 文档 / 重构** → 自动走"当前版本",不再追问版本与分支,直接提交推送。
3. **提交信息**:Conventional Commits(`feat:`/`fix:`/`docs:`/`refactor:`/`test:`);新功能用 `feat:`,并在描述中注明目标版本号(如 `feat: ... (v0.0.2)`)。

## 发布前验证

- `./mvnw test` 全部通过。
- 升版本后确认构建产物名称为 `seeker-share-X.Y.Z.jar`。

## 示例对话(新功能)

```text
用户:新增一个工具
AI:本次属于新功能,默认从 main 切 feature/xxx 分支;
    建议升版本至 0.0.2(默认 MINOR+1),是否确认?还是要 0.0.1 的 PATCH 或当前版本不升?
用户:确认 0.0.2
AI:执行:切分支 → 开发 → ./mvnw test → 更新 pom 至 0.0.2 →
    提交(feat: ... (v0.0.2))→ 合入 main → 打 tag v0.0.2 → 推送。
```
